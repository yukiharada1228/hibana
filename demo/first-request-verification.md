# 初回応答とHTTPストリームの追加改善

2026-09-08、動画と同じWasm・同じCPU/メモリ割当で追加修正を検証しました。各Workerの初回HTTP応答は、修正前の30.823〜58.063 msから、最終版では16.344〜24.193 msになりました。通常時の中央値は約10 msです。初回は2 Workerを2回ずつ測った結果であり、すべての環境でこの範囲に収まるという保証ではありません。

全コマンド出力、Pod設定、HTTP応答、DBの実行履歴、段階別ログは[`public/first-request-verification.json`](public/first-request-verification.json)に保存しています。途中の実装や遅かった測定も含めて保持しています。前回の[固定費の改善](latency-verification.md)や動画の数値は書き換えていません。

## 修正内容

### 初期メモリの準備

コンパイル済みでも、LinuxではWasmtimeが最初のインスタンス生成時に初期メモリの共有用イメージを作る場合がありました。`PreparedComponent::new`で`initialize_copy_on_write_image`を呼び、この処理を成果物の準備時へ移しました。コンパイル後の読込みとメモリイメージ作成はblockingタスクで行います。これはWasmtimeが提供する[初期化時点を指定するAPI](https://docs.rs/wasmtime/latest/wasmtime/component/struct.Component.html#method.initialize_copy_on_write_image)です。実装にはロックされた36.0.14のソースも確認しました。

ゲストのstart関数・handlerは準備時に呼びません。Storeとインスタンスは引き続き実行ごとに作ります。初期化時にtrapするComponentを使い、事前準備でそのコードが実行されないこともテストしました。

### DB接続とSQLの準備

Workerが使う4本のSQLを接続作成時に解析し、SQLxの接続単位のキャッシュへ登録します。SQLを実行したり、テナント情報を取得したりする処理ではありません。実際の取得・更新は従来どおりテナントを設定したトランザクション内で行います。

接続を1本だけ準備する中間版では、設定取得に使った接続の非同期返却と、実行開始用の接続取得が重なり、初回の接続取得に10.538〜11.457 msかかっていました。起動時から2本を維持するよう変更しました。最大接続数は既存の設定を維持し、上限1本の設定では1本だけ準備します。[SQLxの接続プール設定](https://docs.rs/sqlx/latest/sqlx/pool/struct.PoolOptions.html)を使用しています。

最終版の80リクエストでは、実行取得の直前に接続2本・空き1本があり、取得後も2本のままでした。新しい接続をこの経路で作らず、各Worker初回の接続取得は0.117〜0.225 msでした。

### 小さなHTTP送信の待ち

CPの管理・内部・アプリHTTP、Workerの実行HTTP、ローカルdevで、受け付けた接続に`TCP_NODELAY`を設定しました。Nagleのアルゴリズムによる小さな送信の待ちを回避します。[Axumの設定方法](https://docs.rs/axum/0.8.9/axum/serve/trait.ListenerExt.html)、[TokioのTCP_NODELAYの説明](https://docs.rs/tokio/latest/tokio/net/struct.TcpStream.html#method.set_nodelay)に沿った変更です。

修正前にはヘッダー到着から本文完了まで40.641 ms待つリクエストがありました。最終版の80件では最大4.738 msでした。個々の40 msの待ちをNagleに起因すると確定するパケット解析はしていません。本文を保持する上限や、結果を保存してからEOFを返す順序は維持しています。

## 実測結果

各回40リクエストを逐次送信し、間隔は50 ms。毎回新しいcurlプロセスで接続し、応答本文の完了までの`time_total`を使います。中央値・p95には初回も含め、p95は昇順38番目（nearest rank）です。単位はms、表は小数1桁に丸めています。

| 記録ラベル | 実装 | 中央値 | p95 | 最大 |
|---|---|---:|---:|---:|
| `baseline` | 今回の修正前 | 9.1 | 22.1 | 44.0 |
| `improved` | メモリイメージ・SQL準備、接続1本 | 17.6 | 74.9 | 320.8 |
| `baseline-recheck` | 修正前へ戻して再測定 | 11.3 | 50.6 | 59.3 |
| `prepared-pool` | 接続を2本へ変更 | 12.9 | 41.6 | 61.1 |
| `prepared-pool-recheck` | 同版でPod交換後 | 10.9 | 29.4 | 54.4 |
| `final` | TCP_NODELAYも含む最終版 | 10.0 | 22.4 | 49.5 |
| `final-recheck` | 最終版でPod交換後 | 10.4 | 16.3 | 17.5 |

「各Workerの初回」は実行IDをPodログに照合して判定しています。最終再測定では、2台目の初回は3番目のリクエストです。

| 測定 | Worker初回のHTTP全体 | 同じ実行のインスタンス生成 | 同じ実行のDBでの取得全体 |
|---|---:|---:|---:|
| 修正前・1回目 | 30.823 / 44.042 | 4.980 / 17.274 | 5.343 / 4.760 |
| 修正前・再測定 | 58.063 / 48.364 | 17.555 / 19.273 | 7.599 / 5.391 |
| 最終版 | 24.193 / 22.446 | 0.322 / 0.281 | 1.961 / 1.549 |
| 最終版・Pod交換後 | 16.616 / 16.344 | 0.167 / 0.219 | 1.244 / 1.374 |

最終版でも49.533 msのリクエストは残りました。その実行ではCP受付が21.648 ms、WorkerのDB COMMITが5.514 msでした。初回の固定費を減らした結果であり、DB・ネットワークを含む遅延をすべて解消した結果ではありません。

## 環境と比較の限界

- Wasm SHA-256: `90ef1c0c03e251ebcf4ece576761e2b76c3a37c81f8601c5b1d6710847e23384`。動画用成果物をコピーし、再ビルドしていません。
- 専用クラスタ: `hibana-latency-check`。CP 2 Pod、Worker 2 Pod。
- Docker VM: 10 CPU、8,319,504,384 bytes（約7.75 GiB）。CPの各Pod上限は2 CPU/2 GiB、Workerは4 CPU/4 GiB。7回すべてでリソース設定が一致しています。
- 修正前イメージ: `hibana-platform:local-e1c04ba5584b7707759cb977ae7ffa678d521c9ea16318f384d93a2d32568191`。
- 最終版イメージ: `hibana-platform:local-38375cc079f7450f56b363d633da628dcd5fea5043457df13ddf4b5ec2899c92`。中間版のイメージもJSONに保持しています。

既存の開発・別検証クラスタが同じVMで動いています。中間版`improved`の測定ではVMのCPU PSI someのavg10が約15%で、最終版の測定では約2.2%、再測定では約0.27%でした。最終版のビルド中にはCPU・メモリ待ちが大きく増えたため、ビルドを終え、待ち時間を置いてから測っています。各実装のHTTP中央値だけで厳密な改善率を算出できる完全に固定した環境ではありません。

最終版の2回の測定では、CP 2 Pod・Worker 2 Pod・PostgreSQL 1 Podの全対象でCPU制限による停止時間、OOM kill、メモリPSI待ち時間の増分が0でした。CPU/メモリ割当を増やして速度を出したものではありません。DB接続の最低数を2本へ増やした点は、実装上のリソース使用の変更です。

## 動作確認と撤去

全280件がHTTP 200、`{"message":"Hello, Wasm!","count":1}`でした。全実行の状態が`succeeded`で、成果物のSHA-256が一致しています。1,880件の段階別計測を実行IDで照合しました。各測定前の実行数は0、40、80、120、160、200、240で、準備のためのゲスト呼出しは加えていません。

Worker単体テスト、Clippy（Worker・CPの全ターゲット、警告はエラー）、実PostgreSQLを使うHTTP回帰テスト、アーキテクチャ検査、RLS lintが成功しました。SQL準備後もテナント設定が変わらず、実行がpendingのままであること、SQLがキャッシュされること、別テナントの実行を取得できないこと、二重取得できないことを確認しています。ローカルHonoでのSecrets・ストリーム・再読込と、Ctrl+C後のポート解放も確認しました。

検証環境の最初の配備は120秒でタイムアウトしました。DBにアプリ・版が作成されていないことを確認し、再実行は9.489秒で完了しました。この失敗も記録に残しており、HTTP応答の280件には含めていません。

最後に`hibana delete hello-hono --yes`でアプリを削除し、一覧が空であることを確認しました。`hibana platform uninstall --cluster hibana-latency-check --yes`で検証基盤を撤去し、当該クラスタのノードが0個であることを確認しました。一時アプリと認証情報も削除しています。

追加の比較には既存の[`scripts/verify-latency.py`](scripts/verify-latency.py)を使えます。`--record 新しい名前.json`で以前の記録を保持し、`restart`で検証用CP・Workerを再作成できます。クラスタ構築後に`setup`、`measure ラベル`、終了時に`cleanup`を実行します。

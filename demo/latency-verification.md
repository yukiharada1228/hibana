# HTTP応答時間の改善とリソースの検証

2026-09-08、動画で使用したHonoのWasmをそのまま使い、HTTP経路の変更前後を専用のkindクラスタで測定しました。CPU・メモリを増やさず、40リクエストの中央値は旧版の11.638〜12.827 msから改善版の10.312〜10.645 msになりました。初回や遅い側の応答にはまだ揺れがあり、動画の218.709 msを常に10 msにできたという結果ではありません。

生のコマンド出力、Podの設定、全応答、実行履歴、実行IDに対応する内部計測、撤去結果は[`public/latency-verification.json`](public/latency-verification.json)、手順は[`scripts/verify-latency.py`](scripts/verify-latency.py)に保存しています。動画と撮影時の実行記録は変更していません。

## 比較条件

- 成果物: `.local/demo-recording-current/app.wasm`。SHA-256は`90ef1c0c03e251ebcf4ece576761e2b76c3a37c81f8601c5b1d6710847e23384`。再ビルドせず、同じ版を使います。
- 専用クラスタ: `hibana-latency-check`。Control Plane 2 Pod、Worker 2 Pod。既存の開発・他の検証クラスタは操作しません。
- ホスト: 10 CPU、16 GiBメモリ。Docker VM: 10 CPU、8,319,504,384 bytes（約7.75 GiB）。
- 以下のリソース設定は4回の測定で一致しています。

| 対象 | CPU request / limit | メモリ request / limit |
|---|---|---|
| Control Plane（各Pod） | 250m / 2 CPU | 512 MiB / 2 GiB |
| Worker（各Pod） | 500m / 4 CPU | 1 GiB / 4 GiB |
| PostgreSQL | 100m / 上限なし | 128 MiB / 512 MiB |

`requests`はスケジューリング等に使う割当要求であり、CPUの実行上限ではありません。Workerが500mで頭打ちになっている構成ではありません。[Kubernetesのリソース管理](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)を参照してください。

各回40リクエストを逐次送信し、間に50 ms待ちます。毎回新しいcurlプロセスで接続し、`time_total`をHTTP応答完了までの時間として記録します。Podの起動・成果物の事前コンパイルは完了済みですが、測定前にゲストのウォームアップ呼出しは行いません。初回も集計に含めます。これは低負荷の局所的な比較であり、最大スループットや本番のSLOを検証する試験ではありません。

旧版→改善版→旧版→改善版の順で測定しました。改善版のビルド中に別の検証クラスタも起動したため、最初の一対だけで判断せず、保存済みのイメージへ戻して両方を再測定しています。再測定の間にはイメージを再ビルドしていません。VM全体の他プロセスまで一定に固定した実験ではありません。

## HTTPの実測

単位はms。p95は40件を昇順に並べた38番目（nearest rank）です。

| 測定ラベル | 初回 | 中央値 | p95 | 最大 |
|---|---:|---:|---:|---:|
| `baseline` | 69.351 | 12.827 | 46.529 | 69.351 |
| `improved` | 107.062 | 10.312 | 34.009 | 107.062 |
| `baseline-recheck` | 59.117 | 11.638 | 56.200 | 59.117 |
| `improved-recheck` | 53.745 | 10.645 | 51.801 | 84.152 |

中央値の低下は最初の比較で約19.6%、再比較で約8.5%です。初回は最初の比較では悪化し、再比較では改善しました。初回や最大値について一貫した改善を主張できる結果ではありません。

全160リクエストがHTTP 200で`{"message":"Hello, Wasm!","count":1}`を返しました。DBの全160実行が`succeeded`で、WasmのSHA-256が一致しています。各回40実行×6段階、計960件の内部計測を実行IDで照合しました。

旧版のイメージは`hibana-platform:local-504504fead606a15cbba726007695a956ff1f426c18a300eab80af55aeb35ffb`、改善版は`hibana-platform:local-1ba2bf3604955ada3db40540f6290583c095218e7ab8bde7724be471bcd08c24`です。どちらにも同じ段階別の計測を入れています。

## 変更内容と内部の所要時間

1. Control Planeは受付時に確定した版IDを転送処理へ渡し、直前の同じ実行レコードのDB再読込を削除しました。
2. 成果物URLの署名発行を準備用APIに限定し、通常の実行時に不要なS3 URLを作らなくしました。`JobMessage.wasm_url`は更新時の互換性のため空文字で残しています。
3. コンパイル済みコードとimport解決済みの`InstancePre`を同じ既存のLRUで保持します。毎回のLinker構築とimport解決を省きます。型付きexportの取得、Storeとインスタンスの生成は各実行で行います。[Wasmtimeの事前リンクによる高速化](https://docs.wasmtime.dev/examples-fast-instantiation.html)に沿った構成です。
4. 実行期限を検査するepochのタイマーを各Runtimeに一つ置き、毎回OSスレッドを生成する処理を削除しました。各Storeは自身の絶対期限を確認します。

再比較の各段階の中央値は以下の通りです。単位はms。段階には親子関係があるため、この表の値をすべて加算してHTTP全体と比較することはできません。

| 段階 | 旧版再測定 | 改善版再測定 |
|---|---:|---:|
| CP受付 | 1.620 | 1.498 |
| CP転送準備 | 0.433 | 0.022 |
| Worker発見 | 0.569 | 0.605 |
| 実行トークン引換え | 1.406 | 1.107 |
| Worker設定取得 | 0.433 | 0.473 |
| キャッシュ取得 | 0.002 | 0.002 |
| Runtime設定・リクエスト準備 | 0.139 | 0.018 |
| リンク・型付きexportの取得 | 0.047 | 0.002 |

固定費を減らした段階には明確な短縮が見られます。一方、通常時のhandlerは約1 msで、実行記録・認証・設定取得・結果保存・ネットワークもHTTP全体の時間を占めます。応答を返し終える前に結果を保存する契約や、テナントの検証、実行を一度だけ取得する処理は維持しています。

改善版再測定の最初の2リクエストでは、インスタンス生成だけで10.451 / 23.064 ms、DBの実行取得で14.917 / 14.488 msかかりました。事前コンパイルが済んでいても、初回のインスタンス生成と接続先の処理まで通常時と同じ時間にはなっていません。この計測だけでは、さらに内側のページフォルト・接続確立・DB処理のどれが何msかまでは分かりません。

## スペック不足だったか

各回の前後にControl Plane 2 Pod・Worker 2 Pod・PostgreSQL 1 Podのcgroup統計を取得しました。4回とも全対象で`nr_throttled`と`throttled_usec`の増分が0、`oom_kill`の増分が0、メモリのPSI待ち時間の増分が0でした。CPUのPSI full待ち時間の増分は、各Pod・各測定区間で約0.4〜4.9 msです。今回の低負荷では、CPU上限やPodのメモリ不足が支配的な原因という証拠はありません。

Docker VM全体では他のプロセスも動いており、測定時のCPU PSI someのavg10は約1〜2%でした。ビルドと複数クラスタが同居する時間帯には環境による待ちも増えるため、ハードウェアの影響がないとは言えません。ただし、撮影時の218.709 msには同じ粒度のリソース統計がなく、その遅延の原因を後からスペック不足と断定することもできません。

この結果からは、まず実装の固定費を減らし、初回を含む遅い側の内訳を計測するのが妥当です。CPUやメモリを増やすことだけで初回・p95まで解消するとは判断していません。

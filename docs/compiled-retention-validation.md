# 公開版のコンパイル結果の保持

2026-09-25に実施したローカル検証の記録です。この後rc.13としてnpm・本番VPSへ反映しました。[本番CDの検証記録](production-cd-validation.md)を参照してください。

## 変更

- 共有先では公開版、直前のロールバック先、pending/runningの実行、期限内の準備予約が参照するコンパイル結果を保持します。
- 2 GiB・256件の回収枠は、保護対象を除いたキャッシュだけに適用します。Pod内の上限は変更しません。
- 全テナントの参照を合算します。参照取得の失敗時は削除せず、準備予約・公開とGCをDBロックで直列化します。
- 再公開時にPodにだけ残っているコードも共有先へ再保存します。通常のHTTPキャッシュヒットには保存処理を追加しません。

## 検証結果

`bash scripts/test-http.sh`は使い捨てPostgreSQL・Redis、ローカルのS3テストサーバー、実際のControl Plane・WorkerとRust Wasmで成功しました。

| 確認 | 結果 |
| --- | --- |
| 4,097種類の公開版を複数テナントで保持 | 旧256件・4,096件の走査制限を超えても保護 |
| 各保護対象に55 MiBの論理サイズを設定 | 合計が2 GiBを超えても保護対象は回収されない |
| 直前の版、pending/running、準備予約 | 回収されない。実行完了・予約解除後は回収可能 |
| 同じ元Wasmを別テナントでも公開 | 片方のアプリ削除後も保持。最後の参照解除後に回収 |
| 保護対象外のキャッシュ300件と期限切れ予約 | 古いものを回収し、256件の枠を維持 |
| DBの参照関数の実行権限を一時的に取り除く | 保存は503、既存オブジェクトは削除されない |
| 別DB接続でGCと準備予約・公開を競合させる | 相互排他を確認。古いトランザクション時刻で期限切れ予約を再利用しない |
| 共有コピーだけ削除し、Pod内の結果から再公開 | 再コンパイルせず共有コピーを再作成 |
| 続いて空のWorkerへ交換 | HTTP 200、共有キャッシュhit、再コンパイル0回 |
| 改ざん・小さいローカル容量・共有保存失敗 | 既存の検証・復旧動作を維持 |

4,097件の検証はDB参照とS3一覧のメタデータを使います。55 MiBの実データを4,097個保存した試験ではなく、VPSの収容能力や速度を示すものではありません。空のWorkerへの復元は実際の認証済みコンパイル結果で確認しています。

Rustのユニットテスト、`cargo clippy --locked --workspace --all-targets -- -D warnings`、format、architecture、RLS lintも成功しました。初回の並列検証では既存の高負荷drainテストがタイムアウトしましたが、他のテストとの並列実行を終えてからの`test-http.sh`全体は成功しています。

## 適用と容量

新しいControl Plane・Workerの起動前に`m20260925_000014_compiled_retention`を適用します。旧Control Planeは公開版を保護せず回収するため、更新中の混在は避けます。既存の元Wasm・公開先・認証情報は変更しません。

共有先の必要容量は公開版とロールバック先の数に応じて増えます。保存済み結果の容量による削除を防ぐ変更であり、保存失敗・手動削除・実行エンジンの互換性変更による再コンパイルまでなくすものではありません。[設計](architecture.md#公開前のコンパイル)も参照してください。

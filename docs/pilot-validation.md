# MVP試用受入の検証記録

2026-09-08に、CLIから実用APIを配備し、Kubernetes・PostgreSQL・Redis・MinIOを使って検証しました。**修正後の10分負荷と保守復帰は成功しました。2時間の継続負荷は未再検証で、先の不合格記録を維持しています。** 先の試験と修正後の追加試験を分けて記載します。作者以外の開発者による試用は未実施です。

## 環境と候補イメージ

- 専用kind `hibana-mvp-check`。単一の物理ホスト上にControl Plane 2 Pod、Worker 2 Podと依存サービスを配備。
- 固定ホストポートを使わず、明示したkubeconfig・contextに`hibana platform install`で導入。
- テスト用在庫サービスは内部Dockerネットワークに隔離。一般の外部サービスへ負荷を送っていません。
- 通常の配備・rollbackはRead・Deployトークンを使用。Secrets登録・利用許可・版ごとの外向き通信承認にはテナント管理者を使用。
- 各試験で作った専用クラスタ・在庫サービス・ネットワークは撤去済み。既存の開発クラスタは操作していません。

同じ候補イメージを長時間試験と復元試験に使用しました。Docker側のイメージIDは`sha256:40491ead1291c2acd5e2d96deb6db2b933bd041305c8566982370f7522af711c`、全CP・Worker Podが報告したmanifest digestは`sha256:739504747001eaba7bffa32b45426e299d3c820b4ed708ab5fe70ab8ff0cd39a`です。

## 長時間試験：不合格

4並列、各クライアントがリクエスト間に100ms待つ条件で2時間を要求しました。HTTP失敗0という条件を満たさなかったため、約64分で停止しました。

| 観測項目 | 結果 |
| --- | --- |
| 停止前最後の30秒集計 | 84,277件、200が84,268件、502が9件 |
| 失敗した実行の分類 | Secrets取得の通信失敗またはタイムアウト8件、Worker転送失敗1件 |
| 30秒ごとのp95 | 約56ms〜10.6秒。全期間のp95ではありません |
| 観測した最大応答時間 | 約12.3秒 |
| Worker再起動・置き換わり | 121回の資源観測でいずれも0 |
| Workerメモリ | 各Podの観測ピークは約494 / 512MiB、最後の観測は約207 / 207MiB。追加アプリのコンパイルも含む |
| コンパイル済みキャッシュ | 各Podの最後の観測は約323MiB |
| DB容量 | 約8.8MiBから約144.8MiBへ増加。最大接続数30 |

同時刻に、他のkindクラスタも同じDocker VMで稼働していました。VMは10 CPU、load averageは約43、CPU pressureの`some avg10`は62.49%でした。資源競合の影響が疑われますが、この観測だけで原因を一つに断定できません。Wasmや基盤側の問題を除外したとも判断していません。

予備試験で見つけた別の問題として、公開HTTPの既定値50req/s・burst 500に対し、Secrets取得の既定値が600回/分でした。この不整合を3,500回/分へ修正し、受付済みの既定トラフィックが内部制限を超えないことを回帰テストで確認しました。上記9件はその修正後の試験であり、再度の429ではありません。

## バックアップ・復元確認：成功

同じ候補イメージで別の専用クラスタを作り、30秒の短時間試験と復元確認を実施しました。

- 負荷は約30.16秒で708件、失敗0。観測した最大応答時間は約351ms。
- 受付停止と処理待ちの後、DB・S3オブジェクト5件・鍵をバックアップ。
- DBダンプを別の一時DBへ復元し、件数の一致とSecretsの実復号を確認。S3バックアップのハッシュも確認。
- 再起動後はアプリの準備中503を36回観測し、約21.56秒でヘルスチェックが成功。
- その後、在庫照会・Secrets・CLIによる双方向のrollbackが成功。専用環境の撤去も成功。

稼働DBの上書き復元や、別クラスタへのDB・S3を含む全体復旧は、この試験の対象に含めていません。準備中の503は保守からの復帰過程として記録しており、長時間試験中に発生した9件の失敗は不合格のままです。

受入スクリプトについても、復元後の接続先ファイルの更新を修正し、アプリの準備時間と失敗段階を記録するよう改善しました。負荷が失敗しても、独立した復元結果を残します。

## 再現と残る条件

[試用受入手順](pilot.md)に沿って実行します。主なスクリプトは`kubernetes.py`（全体）、`application.mjs`（実用API）、`version-code.mjs`（コードとvarsの切替）で、いずれも`scripts/acceptance/`にあります。

今回の記録は`.local/mvp-acceptance/20260907T233527Z/`（長時間試験）と`.local/mvp-acceptance/20260908T005754Z/`（機能・復元の最終試験）にあります。これらのフォルダには認証情報・鍵・バックアップが含まれるため、共有・コミットしません。

次の受入ではCPU・メモリ・I/Oを確保した専用の検証環境を使い、Secrets取得とWorker転送の遅延を計測しながら2時間試験を再実行します。実行記録の保存期間、内部IPへの接続要件、別の開発者が手順書だけで導入できるかも確認が必要です。実ノード喪失、TLS、CNIによる分離、DB・Redis・S3のHA切替は、本番候補環境の別の受入条件です。

## 修正後の追加試験：600秒負荷と保守復帰

2026-09-08 01:37〜01:51 UTCに、専用kind `hibana-mvp-repair`で実施しました。記録は`.local/mvp-acceptance/20260908T013729Z/`です。イメージIDは`sha256:435e1b4190ac754df250c05857551b704669aa13628e4c3abf7812ab503d7386`、CP・Workerの実Pod manifest digestは全4 Podで`sha256:a7ef4a6908db290de0fdb0151682fd54cbf4d4870f23c995d83a4a3dd9dc6771`でした。

次を修正しました。

- Secret注入のDB読込みを認可に必要な項目に限定し、世代解決と未解決検出を1回のSQLに統合。世代固定・版の参照・RLSを維持。
- Secrets取得のタイムアウト・接続失敗・HTTP拒否・本文不正を安全な分類とメトリクスへ記録。Worker転送も失敗段階と所要時間をログに記録。
- 保守からの自動復帰は全active版を全Workerで準備し、キャッシュ確認とPod交換・再起動の検査を終えてから受付再開。失敗時はゲートを維持。

| バックアップ | DB・S3オブジェクト5件・鍵を保存。別の一時DBへの復元、件数・実Secret復号・S3バックアップのハッシュ確認が成功 |

Workerメモリの観測ピークは約542 / 533MiB、コンパイル済みディスクキャッシュは各約208MiBでした。VMのCPU pressure `some avg10`は観測最大21.41%で、共有ホストによる試験です。これを専用環境での長時間安定性の証明とは扱いません。前回の9件の502の原因を一つに確定したわけでもありません。

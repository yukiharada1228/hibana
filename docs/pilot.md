# MVPの試用受入

対象は自組織の開発者によるHTTP APIの試用です。作者以外の開発者による導入確認と、自動テストの結果を分けて記録します。

[2026-09-08の検証記録](pilot-validation.md)：初回の負荷試験は不合格、修正後の2時間試験と復元・停止再開は成功しています。これはv0.1.0時点の結果であり、以降の版の長時間試験とは区別します。

## 開発者へ渡すもの

管理者はバージョンを固定したCLI・ランタイム、管理APIのHTTPS URL、アプリ用ドメイン、テナント名、組織のOIDCアカウントとRead・Deploy権限を用意します。開発者はブラウザでログインします。自動試験には専用APIトークンを使います。試用する開発者にkubeconfigは渡しません。Secretの登録・利用許可と外向き通信の承認はテナント管理者が担当します。

自動試験には、テスト専用の[認証付き在庫照会API](../sdk/test/fixtures/inventory-api.ts)を使います。接続先はこのAPIの契約を満たすHTTPサービスです。自動試験ではテスト用の在庫を使います。実際の業務で役立つかどうかの検証には、利用者が必要とする接続先とデータを別途用意します。

## 自動試験とリリース候補

最新のrc.10では[2時間の負荷・履歴清掃・復元試験](retention-validation.md)が合格しています。

`scripts/acceptance/kubernetes.py`はポート固定なしの専用kindを作り、明示したKubernetesコンテキストへCLIで導入します。CPとWorkerは内容に基づく同じイメージタグを使い、実PodのimageIDと、アプリの更新前後のWasm SHA-256を記録します。

コードに書いた値と環境変数を別々にHTTP応答へ返す小さなAPIも使い、更新と双方向のrollbackで両方が揃って切り替わることを確認します。Wasmのハッシュが異なるだけでは成功としません。

認証・Secrets・HTTP通信・不正入力・外部エラー・コードとvarsの更新・rollbackを確認後、並列4、各クライアントがリクエスト間に100ms待つ条件で2時間動かします。最大投入量は40req/s未満です。これは最大性能の測定ではありません。HTTPステータス・本文・版を検証し、30秒ごとに応答時間、Workerのメモリ・キャッシュ・再起動、DB容量・接続数・実行数を記録します。

負荷中は停止中の試験テナントに期限切れ履歴を5分ごとに6,000行投入し、150秒以内の削除と利用量・監査・直近履歴の保持を検証します。並行して配布CLIの`tail --format json`を監視し、切断・欠落警告・重複・秘密値の混入がないこと、HTTP 200/404とアプリ出力が揃うこと、保存ログと一致することを確認します。

[手動ワークフロー](../.github/workflows/acceptance.yml)は専用GitHub Actionsランナーで120秒の通し試験後に2時間試験を実施します。成果物は秘密値を含まない結果・負荷・リソースの記録に限定し、資格情報・DBバックアップ・kubeconfigはアップロードしません。

HTTP失敗を検出すると負荷を停止し、既に送信したリクエストの完了を待ちます。負荷の不合格とバックアップ・復元の結果は別々に記録し、復元の成功で負荷の失敗を相殺しません。`--seconds 30`で機能・復元確認を短時間で再実行できますが、2時間の受入条件を満たしたとは扱いません。

バックアップを別DBへ復元し、Control Plane・Worker・マイグレーションの接続先を復元先へ切り替えます。アプリの準備完了後に受付を再開し、最初のHTTPリクエストから200を必須にします。Secretsを使った在庫照会・再配備・双方向のrollbackを確認し、復元先だけに新しい実行が保存されたことも検証します。

合格にはHTTP失敗0、Worker再起動・置き換わり0、観測の欠落0、バックアップから別DBへの復元・Secretsの実復号成功、保守後のAPIとrollbackの成功を必要とします。DB復元は稼働DBを上書きせず別DBへ実施します。S3オブジェクトはバックアップ時に取得してハッシュを確認しますが、この試験だけで別クラスタへの全体復旧やS3フェイルオーバーを実証したとはしません。

このkind試験は単一の物理ホスト上で動きます。実ノード喪失、強制力のあるCNIでの分離、TLS、複数台DB・Redis・S3の切替、実Ingress/LBでの迂回は、本番候補環境の別の受入条件です。

## 容量設定で注意する点

公開HTTPのレートと、Secret取得用の内部APIのレートは別の設定です。以前の既定値では公開HTTPは50req/s・burst 500、Secret取得は600回/分だったため、正常に受け付けたSecret付きAPIが負荷時に502になることを在庫APIの試験で確認しました。Secret取得の既定値を3,500回/分へ変更し、公開HTTPの既定レートとburstを扱えるようにしています。

`JOB_ENV_EXCHANGE_RATE_PER_MIN`はテナント単位と接続元IP単位の両方へ適用されます。既存環境で`600`を明示している場合は、その設定も更新してください。新しい既定値が使われるのは未指定の場合です。テナントのレートを増やしたり、多数のテナントを同じWorkerに収容したりする場合は、この内部予算も運用側で合わせます。設定の引き上げにはCP・DBの負荷検証が必要です。

実行記録はリクエストごとにDBへ保存されます。rc.10以降では[保存期間と自動削除](database.md#実行履歴の保存期間)を設定できます。試用期間・保存日数・DB容量を決め、記録数・期限超過行の滞留・DB容量・バックアップ容量を監視します。2時間の成功だけで、容量を増やさず無期限に運用できるとは判断しません。

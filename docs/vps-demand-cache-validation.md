# Pod内キャッシュ容量を超えるWorkerの検証

2026-09-25にローカルで実施。本番VPS・npm公開版は変更していません。[集計データ](vps-demand-cache-validation.json)。

## 変更

公開アプリ全件を各Podへ常駐させる前提を外しました。公開中のコードもローカルキャッシュから退避でき、リクエスト時にメモリ→ローカルファイル→認証済みGarageキャッシュ→元Wasmの順で解決します。元Wasmは削除しません。コードの参照を実行終了まで保持し、保存失敗時も検証済みのコードをメモリから実行します。

全件を5秒ごとに読み直す処理と、全件の常駐を要求する起動readinessを削除しました。実行トークンで指定されたpendingの版だけを復元し、完了後に権限・実行状態を再確認してからDBの実行権を取得します。復元は同時実行枠・コンパイル枠で制限し、85秒で打ち切ります。期限切れ・失敗時にゲストを自動再実行しません。

## 条件

- 同じMac上のUbuntu ARM64 VM 3台、各2 vCPU・2 GiB、swapなし。kubeadm Kubernetes 1.36.5、Calico。
- 実行Pod 1台。request 768 MiB、limit 1280 MiB、CPU limit 2、ゲスト予約1024 MiB、同時実行8、同時準備1。
- ディスクキャッシュを`WORKER_CACHE_DISK_MIB=128`へ縮小。メモリLRUの256 MiBは変更なし。
- SHA-256の異なるHonoアプリ8個。各コンパイル結果54,466,512バイト（約51.94 MiB）。全8個では約415.55 MiB。
- 既存helloも保持。Podはアプリの切替えで再作成せず、HTTP本文がそれぞれのアプリと一致することまで確認。

## 結果

8個すべて公開成功。ローカルファイルは最大2個・108,933,024バイト（約103.89 MiB）で、128 MiBの枠内でした。

| 試験 | 成功 | HTTP中央値 | p95 | 最大 |
|---|---:|---:|---:|---:|
| 8アプリを順に3周 | 24/24 | 393.383 ms | 507.77 ms | 539.199 ms |
| 直前に使った同一アプリ | 50/50 | 11.423 ms | 26.902 ms | 28.035 ms |
| 空の新Podへ同じアプリを4件同時 | 4/4 | 930.267 ms | 932.352 ms | 932.352 ms |

HTTP接続・TLS・Control Plane・コード復元・実行・結果保存を含む時間です。コードの切替えだけの時間ではありません。同時4件のp95は標本が少ないため最大値と同じです。

8アプリ巡回では共有キャッシュhitが24増加し、コンパイル回数は増えませんでした。空の新Podは全件コンパイルせずReadyになり、4件同時でも共有取得1回・メモリhit3回・コンパイル0回でした。DNSの切替え完了後に測っています。メンテナンスの全active版検証も、全件がローカル容量に収まらない状態で成功しました。

主試験の実行Podは、1秒間隔114標本でworking set最大413.08 MiB、OOM kill 0・再起動0でした。瞬間的なピークを取り逃す可能性があります。

## Pod交換とDNSの追加確認

キャッシュの入替えはPod交換を伴いません。別試験で唯一のPodを削除すると、新PodのReady後もCoreDNS（TTL 30秒）が旧IPを返し、4件が約3秒の接続タイムアウトで502になりました。実行は再送していません。

標準のRollingUpdateマニフェストへ`preStop`の35秒待機を追加しました。DNSに古いIPが残る間は旧プロセスが応答し、その後SIGTERMでdrainします。終了猶予90秒に待機時間も含まれるため、DNS TTLやdrainを増やす運用では猶予も調整します。[KubernetesのPreStop仕様](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)。

追加のRollingUpdate試験だけはrequestを512 MiBへ下げ、新旧Podを並行配置できる条件にしました。100件中100件成功、旧Podが消えたことと新Podの共有hit 1・コンパイル0を確認しました。この一時的なrequest変更は最小VPS用IaCへ反映していません。

最小VPS構成のrequest 768 MiBでは新旧2台を同時配置できず、35秒の待機だけでは無停止になりません（50件中30件成功）。VPS用IaCは従来のRecreateを維持し、この待機を外して旧Podの予約を速やかに解放します。Pod交換・ノード障害の無停止を保証する構成ではありません。補助試験の配置変更中にDB接続の起動時タイムアウトが1回ありましたが、主試験の実行Podでは発生していません。

## 回帰検証と後片付け

Rust単体323件・doc test 1件、実HTTP回帰試験、clippy、fmt、architecture・RLS lint、プラットフォーム245件、IaCレンダラ5件を確認しました。容量を超えた成果物のメモリ実行、退避後の参照維持、重複復元の抑制、共有データ改ざん、テナント境界・削除・キャンセルも検証しています。物理ディスクを満杯にするENOSPC実験は行っていません。

作成した8アプリはAPIで削除し、一時APIトークンを削除。検証クラスタのDeployment仕様・キャッシュ鍵を元へ戻し、既存helloの応答を確認しました。停止していたローカルHibana 2環境も元のコンテナ・設定で復元し、API・Console・OIDCを確認しました。検証VMは停止しています。試験用の削除済みアプリ履歴・元Wasm・使い捨ての共有キャッシュは検証ストレージ内に残ります。

保持数は元Wasmの保存容量にも依存します。共有キャッシュは既定2 GiB・256件なので、そこからも退避されれば再コンパイルが必要です。ローカルの上限は名前付きファイルの論理量で、実行参照が保持する削除済み領域・一時ファイル・RSSは別途予算が必要です。この小さいHonoアプリの結果を、任意の重いアプリや実VPSの性能保証には使いません。

# Hibana HTTP MVP

Hibana は、Web API を Wasmtime 上で実行するセルフホスト型 Wasm サーバレス基盤です。
サーバーの実行契約は WASI HTTP Component (`wasi:http/incoming-handler@0.2.3`) に統一します。
Hono は JS/TS の選択肢の一つであり、サーバーは言語やフレームワークに依存しません。

実装の責務分担と変更時の依存方向は[アーキテクチャ](architecture.md)で管理します。

## 残す範囲

- GitHubから単独で導入する`hibana` CLIと、OS別のローカルランタイム。
- `hibana init / build / dev / deploy / delete`、リモート接続プロファイル、認証、環境変数、Secrets。
- 管理者による既存Kubernetesへの基盤導入・停止・再開・撤去。
- Hono、通常の JS/TS、Rust、Go のテンプレート。
- HTTP の入出力、バイナリ、ストリーミング。
- 実行時間・メモリ・同時実行数の制限、テナント分離、既定で拒否する外向き通信。
- バージョンの切替と、直前の版または指定した版への単純な rollback。
- 実行結果・利用量の記録、ヘルスチェック、メトリクス、停止時の処理待ち。
- Kubernetes の Control Plane / Worker と PostgreSQL、Redis、S3 互換ストレージ。

## MVP から外す範囲

- Canary、重み付きルーティング、専用の promote 操作。
- 独自の bytes handler、非同期ジョブの `/invoke`、大入力用 `/uploads`。
- NATS、outbox 配送、配送再試行、DLQ、テナント別 consumer、キュー量ベースのスケール制御。
- Workers / Wrangler の完全互換、汎用 CLI バッチ、任意の WIT 契約、独自の DB / KV / Queue サービス。

テナントの同時実行数は、DBの受付記録をテナントごとの短いトランザクションロック下で確認します。Redisの再同期でカウンタが少なく見えても上限を超えて受け付けません。

Redis は起動時に必須です。稼働中に共有カウンタを確認できなくなった場合も、HTTP受付を503で拒否して制限の喪失を防ぎます。

HTTP リクエストは自動再実行しません。通信失敗時には、関数の外部への副作用が既に発生した可能性があります。
Workerが実行前に容量不足を明示した場合だけ別Podへ送ります。転送失敗時は未取得の`pending`だけを終了させ、受付枠を返します。実行中の通信障害にはこの返却を適用しません。[過負荷制御とHPA](scaling.md)を参照してください。
実行結果の保存だけは冪等に扱い、保存の再試行で関数を再実行しません。
rollback はコード・環境変数・選択したSecretsの参照を同じバージョンへ戻す操作です。Secretsの値・外部DBは巻き戻しません。配備はこれらの設定とactive版を一つのDBトランザクションで公開します。通常の開発者はRead・Deploy、Secretsの利用許可はテナント管理者が担います。

## 変更ごとのレビュー基準

1. Web API の開発・配備・運用、または実行境界の安全性に必要か。
2. 四つの言語テンプレートが同じ HTTP 契約とランタイムを利用できるか。
3. 常駐プロセス・永続状態・公開 API を増やす場合、その必要性を説明できるか。
4. 削減によって認証・テナント分離・Secrets・実行制限・復旧手段を失っていないか。
5. 正常系だけでなく、失敗時の挙動を検証できるか。
6. [セキュリティ境界](security.md)の保護対象・既定拒否・依存監査を維持し、未検証の安全性を保証済みと表現していないか。

新機能の追加より、四つのテンプレートで `init → dev → build → deploy → HTTP → rollback` が再現できることを優先します。
[試用受入](pilot.md)では、認証・Secrets・外向きHTTPを使う実用APIと、作者以外の開発者による導入を確認します。自動試験と人による試用の結果は分けて記録します。
本番対応は別の受入段階とし、依存サービスの HA / バックアップ復元、負荷・障害試験、監視、鍵管理を検証します。
単一ホストの kind / Compose 上の検証は、本番の可用性を保証しません。

## 既存環境からの更新

既存マイグレーションと過去のジョブ関連テーブルは履歴・データ保全のため残します。
新しいランタイムは古いジョブを再配送しません。更新前にHTTPと非同期の受付を止め、実行中の処理を完了させてください。この変更では内部実行契約も変わるため、旧版と新版を混在させた無停止更新は保証しません。
旧 Canary の設定が残っていても、新規 HTTP リクエストは active version のみを使います。

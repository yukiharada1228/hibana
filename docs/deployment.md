# デプロイ・環境変数・Secrets

HibanaのHTTP MVPは、Wasmコード・vars・使用するSecretの参照をバージョンごとに固定します。通常の開発者はRead・Deployスコープで`hibana deploy`と`hibana rollback`を実行できます。Kubernetes権限もテナントのAdmin権限も必要ありません。

## アプリの設定

```json
{
  "name": "my-api",
  "main": "src/index.ts",
  "vars": { "GREETING": "Hello Hibana" },
  "secrets": ["API_KEY"]
}
```

`vars`は平文です。`secrets`は使用する名前だけの配列で、省略時は空配列です。同じ名前を両方には指定できません。名前は英大文字・数字・アンダースコア、先頭は英大文字かアンダースコアで、64文字以内です。両者の合計は64件以内、値は1件4KiB以内です。選択したSecretも含め、名前と値の合計をUTF-8で32KiB以内に収めます。サーバーが配備時に合計を確認し、上限を超える版は公開しません。

Secretの更新・ローテーション時も、そのSecretを参照する削除されていない全バージョンを確認します。切り戻し可能な過去の版も対象です。どれか一つでも上限を超える場合は`409 Conflict`となり、元の値と世代を保持します。参照していないSecretと削除済みの版は合計に含めません。旧データなどが実行時に上限を超えた場合も、Workerは設定を一部省略して続行せず、アプリの実行前にエラーにします。

暗号化鍵の再ラップ（`POST /admin/secrets/rekey`）も、値更新・削除・配備と同じアプリ単位のロックを使います。ロック取得後に最新世代を確認し、更新済み・削除済みの対象はスキップします。

初回は`secrets: []`でアプリを配備します。管理者がそのアプリにSecretを用意してから、設定に使用する名前を追加してください。

```sh
# テナント管理者の認証情報で実行
hibana secret put API_KEY < /path/to/value.txt
hibana secret allow-deploy API_KEY

# hibana.jsonのsecretsへAPI_KEYを追加し、開発者の認証情報で実行
hibana deploy
```

Secretを保存しただけでは利用許可になりません。AdminスコープとAdminロールで`allow-deploy`したものだけを、以後のDeploy権限による配備で選択できます。許可の単位はテナント内のアプリとSecretです。トークンそのものはテナント単位であり、同じテナントのDeploy権限保持者はそのアプリのコードを更新できます。

`hibana secret deny-deploy API_KEY`は今後の配備への許可を止めます。既存バージョンとその版へのrollbackは許可されたままです。`hibana secret delete API_KEY`は既存の版も含めて以後の注入を停止します。既に実行中のアプリが取得した値は回収できません。削除後に同名Secretを作り直しても、古い版の参照は新しいSecretへ付け替わりません。

## 公開とrollback

新しいバージョン名は1〜128文字のASCII文字列で、先頭を英数字、残りを英数字または `.`・`_`・`+`・`-` に限定します。CLIはビルド前に、APIはWasm検証・保存前に確認します。旧版で登録された名前は変更せず保持します。

詳細取得と削除には `GET` / `DELETE /components/{component_id}/versions/by-id/{version_id}` を使えます。コンソールもこの固定IDを使うため、旧版の `.`・`..` などを含む履歴を操作できます。従来の `/versions/{version}` は名前指定の互換APIとして維持します。ID指定でもRead/Adminスコープ、テナント・アプリの照合、現在の版・切り戻し先・実行中の版の削除保護を適用します。

アプリ・バージョンの削除は、`audit_logs`へ`component_deleted`・`version_deleted`として操作元と対象IDを記録します。操作元はユーザーID、ユーザーに属さないトークンではトークンID、基盤管理APIでは`bootstrap`です。削除と監査ログは同じトランザクションで保存し、監査ログを保存できなければ削除も取り消します。

CLIは`POST /components/{id}/versions`のmultipartにWasm、`vars`、`secrets`、`activate=true`、`ingress=true`を一緒に送ります。サーバーは受信・隔離検証・S3保存を終えた後、短いDBトランザクションで次を実行します。

1. テナントとアプリの生存状態、署名ポリシーを再確認。
2. バージョンを作成し、選択したSecretの利用許可を確認。
3. varsとSecretのID参照を保存し、合計サイズを検証。
4. active版と公開設定を更新してcommit。

署名検証で拒否する場合は、公開処理に進む前に `component_signature_rejected` の監査ログだけをcommitします。署名の欠落・登録鍵の不在・不正な形式・署名の不一致を記録し、署名本体や秘密値は監査ログに含めません。

途中で失敗すれば、稼働中のコード・vars・Secret参照・公開設定は変更されません。受信とS3操作の間はDBトランザクションを保持しません。新規アプリの作成は別操作なので、初回配備に失敗すると未公開の空アプリが残る場合があります。S3保存後の失敗で未参照の成果物が残る場合もあります。S3とDBをまたぐ分散トランザクションではありません。

HTTP受付時にexecutionへバージョンIDを固定し、Workerはその版のvarsを読みます。受付後に別の版が公開されても、コードとvarsの組み合わせは変わりません。`rollback`はコード・vars・Secret参照を戻します。Secretの値は実行受付時点で有効な世代を使用するため、コードを戻してもSecretのローテーションや外部データは巻き戻りません。外向き通信の許可は管理者によるアプリ単位の設定です。Workerの実行準備時に現在の設定を読み、ロールバックでも許可は変わりません。

HTTP受付とSecret更新は同じアプリのロックで順序を揃え、ロック取得後のDB時刻を記録します。Workerが値を取得する前に次の更新が完了しても、受付後に作られた世代は選びません。

同名アプリの初回配備が重なった場合、アプリ作成APIは重複を`409 Conflict`で返します。CLIはその場合だけアプリを再取得し、先に作成されたアプリへ配備を続けます。バージョンのアップロードは自動再試行しないため、並行配備には異なるバージョン名を指定してください。

## DBの初期化と切替

バージョンAPIは`status`を返しません。公開状態はアプリの`active_version_id`で確認します。アップロードのmultipartは`version`・`wasm`・`signature`・`resource_limits`・`vars`・`secrets`・`activate`・`ingress`だけを受け付け、旧`capabilities`や未知の項目は400で拒否します。実行権限は検証済みWasmのimportと承認済みの環境変数・Secretからサーバーが確定します。

現行版への更新では、受付停止・実行完了待ちの後に全Control PlaneとWorkerを停止し、`0.2.0-rc.7`では`m20260923_000013_application_logs`までのDB変更と認証設定を適用して、両方の新版を起動します。アプリ共通の外部通信設定がなかった場合は全拒否になるため、必要な通信先を管理者が設定してから受付を再開してください。旧版との混在運用はサポートしません。`AUTH_MODE`を削除し、既存管理者を確認済みOIDC subjectへ紐付けてください。パスワード認証からの切り替え時に全トークンが失効するため、再ログインとAPIトークンの再発行が必要です。パスワードハッシュを削除する変更なので、事前にバックアップを取得し、[認証の切り替え手順](authentication.md)に従ってください。

このソースはSeaORMの新しい初期スキーマを使用します。旧SQLマイグレーションを適用したDBへの上書き更新には対応しません。空の検証DBへ初期マイグレーションを適用し、CP・Worker・CLIを同じソースから用意して確認します。既存DBはそのまま保持し、切替は別の保守作業として行います。[基盤DBの手順](database.md)を参照してください。

ORM 基盤からの更新には追加マイグレーション `m20260917_000004_execution_input_retention` と `m20260917_000005_execution_input_cleanup` が必要です。停止中のテナントを含む完了済み HTTP 実行の入力・入力参照を削除し、受付済み・実行中の入力と版・実行結果・利用量を保持します。削除した入力は rollback で復元しません。更新後の実行詳細 API も `input`・`output`・`input_ref`・`output_ref` を返しません。マイグレーション後に旧 CP が完了した実行の入力は、新 CP の定期清掃で回収します（停止中のテナントも対象、既定30秒周期・1テナント最大500件ずつ）。

鍵の参照件数を正しく数えるため、`m20260918_000006_secret_key_retention`もCP・Workerの更新前に適用します。再暗号化後も、未完了の実行が必要とする旧Secret世代を数えます。旧鍵を撤去する手順は[基盤DBの手順](database.md)を参照してください。

同名ヘッダーの全値は、バイト列と順序を保持する一つの形式で送ります。旧形式との互換処理は持たないため、受付を停止して実行中リクエストを完了させ、CP・Workerを同じ版へ更新してから受付を再開してください。

varsとSecret参照の変更には新しいバージョンを配備します。設定APIは参照専用です。旧`PUT /config`・`DELETE /config/{key}`・版ごとのenv承認PUTは削除しました。既存クライアントでこれらを呼んでいた場合は、`hibana.json`を更新して`hibana deploy`を実行する方式へ変更してください。

## プロキシ経由のログイン

コンソールや Ingress を経由する場合、Control Plane の `TRUSTED_PROXY_CIDRS` に、そのプロキシの接続元 IP 範囲をカンマ区切りで設定します（単一 IP は `/32` または `/128`）。例は `10.20.1.0/24,10.20.2.10/32` です。これは基盤管理者の設定であり、アプリの `hibana.json` や CLI のログイン引数には不要です。

コンソールと Ingress の両方を通る構成では、両方の接続元範囲を指定します。通常の利用者や信頼できない Pod を含む範囲は指定しません。最外周の Ingress は `X-Forwarded-For` を実際の接続元で上書きするか、自身の接続元を追加し、既知の上流プロキシだけを信頼するよう設定してください。コンソールは接続元を追加し、CP は右から順に信頼するプロキシだけをたどって利用者の IP を決定します。これにより、別の利用者のログイン失敗で全員がロックされることと、利用者による IP ヘッダーの詐称を防ぎます。

未設定時は直接の接続元 IP を使います。プロキシを含む構成では `hibana platform install` が未設定を拒否します。旧 `TRUST_PROXY_HEADERS=true` は廃止したため、更新前に上記の範囲指定へ移行してください。IP が変わるプロキシには管理された専用の範囲を指定し、共有 Pod CIDR 全体を無条件に信頼しないでください。

## 実行中の停止

Worker は SIGTERM を受けると新規受付を止め、HTTP 応答と実行結果の保存の両方を `WORKER_DRAIN_TIMEOUT_SECS` 内で待ちます。クライアント切断や応答前の Wasm エラーでも保存待ちを継続します。期限を超えた場合は終了し、未確定の実行は既存の定期回収処理で確定します。

テナント停止や実行トークンの期限切れは新規実行を拒否します。受付済みの実行結果は、署名・テナント・実行 ID・固定されたバージョンを照合して保存し、利用量と実行枠を一度だけ更新します。

出力量はHTTP応答本文の累計バイト数です。ストリーミングではゲストのメモリ上限を超える出力も記録し、Workerと共通の応答上限（64MiB）を適用します。

## 検証

`bash scripts/test-http.sh`は使い捨てPostgreSQL・RedisとローカルCP/Workerを使用します。空DBの初期化・旧DBへの適用拒否、権限不足、同時配備、公開失敗、HTTP応答のvars/Secrets、rollback、Secret削除・再作成、RLS・複合FKを確認します。テナント停止後の結果保存、SIGTERM時の保存待ち・終了期限も検証します。S3はこのテストではHTTPスタブです。実Kubernetesの更新・実S3の切替・長時間負荷は別の受入試験です。

環境変数の合計サイズは、UTF-8の境界値、配備・更新失敗時の取り消し、非稼働版の保護とWorkerの実行前拒否を確認します。削除の監査はユーザー・サービストークン・基盤管理APIを対象に、記録失敗時に削除も取り消されることを確認します。

Secretの再ラップは値更新・二重実行・削除との競合を、実DBのロックで順序を固定して確認します。出力量はメモリ上限8MiBのゲストから16MiBを配信し、実行記録と利用量集計が受信量と一致することを確認します。

`node scripts/test-console-proxy.mjs` は使い捨てNginxコンテナでコンソールの設定を読み込み、直接アクセスと多段プロキシのIP転送を確認します。既定はコンソールDockerfileと同じNginxイメージです。ビルド済みコンソールを使う場合は `HIBANA_CONSOLE_TEST_IMAGE` でイメージを指定できます。

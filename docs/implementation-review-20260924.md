# 実装レビュー（2026-09-24）

CLI、Console、Control Plane、Worker、共有型・DB・マイグレーション、拡張、Kubernetes操作コードを対象に、未使用宣言・依存関係・責務の重複・不要な処理・障害時の挙動を確認しました。直前の未コミット変更である`tail`の追加と`logs`コマンドの削除も含みます。

## 解消した指摘

| 指摘 | 修正 |
| --- | --- |
| ライブログがRedisの応答待ち中にもDB接続を保持していた | 対象アプリの確認後にトランザクションを終了。通知がある場合だけ新しいテナントトランザクションで本文を取得する。単一接続のDBプールでも、Redis待機中に別のDB操作が完了することを検証した。 |
| 実行履歴とライブログで、取得する列・テナント条件・ログ保存期限の指定が重複していた | `db::execution_summary_query`へ集約。履歴一覧には本文を含めず、必要な経路だけ本文を取得する。リクエスト・レスポンス本文や参照先を取得しない境界を維持した。 |
| 通知処理がHTTPハンドラに属し、通常完了とreaperでタイムアウト処理が重複していた | `store::tail::publish_completed`へ集約。1件の完了またはreaperの1テナント分について、通知全体を100msで打ち切る。複数通知を遅延させる回帰テストを追加した。 |
| 配備済みアプリの操作が、無関係なローカルビルド設定の検証に依存していた | `tail`・`rollback`・`secret`・`egress`はJSON形式とアプリ名を確認し、ビルド設定全体の検証は`build`・`dev`・`deploy`で行う。ビルド設定が不完全な状態でリモート操作が成功することを検証した。 |
| Consoleが成功HTTP応答のJSON解析・読み取りエラーをそのまま表示できた | 応答の断片を含まない固定メッセージへ変更。変更操作を自動再送せず、状態確認を案内する。不正JSONと途中で壊れるストリームで検証した。 |
| ログごとの日時フォーマッタ生成、Redis操作ごとの同一スクリプト生成、通知順への復元時の反復線形探索があった | フォーマッタとスクリプトを再利用し、取得済み実行をIDで索引化して通知順に取り出す。 |
| アプリ検索が重複し、内部関数が不要にexportされていた | `findComponent`を中断シグナル付きで再利用。内部の表示・拡張名判定関数のexportと、削除コマンドの重複したパス解決を除去した。 |

静的検査では、本体Rust・Console・CLI・自作拡張JSに追加の未使用宣言を確認しませんでした。Rust直接依存の参照とPythonのimportも確認しています。公開済みAPI、過去のマイグレーション、テナント分離・署名・実行結果保存の境界で行う再検証は役割があり、未使用コードとは扱っていません。配布物内の第三者ライブラリ生成コードは修正対象外です。

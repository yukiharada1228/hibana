# 実VPSでのWorkerコールドスタート計測

2026-09-25、公開中の `https://hello.demo.apps.hibana.cloud/` を、Workerのプロセスとコンパイルキャッシュを毎回破棄して3回測定した。**Workerの起動指示から最初のHTTP 200まで26.6〜77.6秒、ダウンロード・再コンパイルからWorkerの準備完了までは約18.1秒だった。** 準備後の最初のHTTP応答は95.7〜110.3ms。

機械可読の結果は [vps-cold-start-validation.json](vps-cold-start-validation.json)。実験後はWorker 1 PodをReadyへ戻し、公開URLのHTTP 200・本文と、Hibanaの全Deploymentの必要レプリカ数を確認した。

## 条件と「冷えた状態」の範囲

- KAGOYA VPS 3台、各2 vCPU・2GB。今回の実行系はHibana Worker 1 Pod。イメージは `0.2.0-rc.10-linux-amd64`。
- `hello` の同じWasm・同じ公開URLを使用。コード・実行上限・DNS設定は変更していない。
- Workerを1→0へ縮小し、旧Podの削除とPod数0を確認してから0→1へ戻した。全試行でPod UIDの変更、キャッシュミスのログ1件、コンテナ再起動数0を確認した。
- コンパイル済みWasmは `/var/cache/hibana` の `emptyDir` に保存される。[KubernetesのemptyDir仕様](https://kubernetes.io/docs/concepts/storage/volumes/#emptydir)によりPod削除で破棄され、新しいPodは空のキャッシュから開始する。メモリ上のキャッシュも新しいプロセスでは保持されない。
- VPSのOS、ローカルのコンテナイメージ、Hibana Control Plane、DB、Redis、Garageは稼働を維持した。それらのキャッシュやOSのページキャッシュは消去していない。今回の結果はWorker／アプリのコールド状態についてのもので、VPS全体の電源投入時間ではない。
- Macから毎回新しいcurlプロセス・HTTPS接続でGET。自動再試行なし。プローブは直列で、開始間隔は最短0.5秒。応答に時間がかかる場合は間隔が延びる。各試行の成功後に5件、計15件のウォーム応答も測定した。

## 結果

| 試行 | Worker起動指示→最初のHTTP 200 | ダウンロード・再コンパイル開始→Worker準備完了 | 準備後の最初のHTTP応答 | 最初のアプリ実行時間 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 77.6秒 | 18.06秒 | 110.3ms | 4ms |
| 2 | 26.6秒 | 18.14秒 | 105.7ms | 4ms |
| 3 | 57.7秒 | 18.12秒 | 95.7ms | 4ms |

起動指示の時間は、このMacでscale-up用のSSHコマンドを開始した時点から、最初の成功応答を受け取り終えるまで。停止・削除にかかった時間は含めていない。コンパイルを含む準備時間は、同一Workerの `component cache: miss; downloading and precompiling` と `active applications prepared; worker ready` のログ時刻差。ダウンロード・コンパイル・ロード・準備状態の確認を含み、コンパイラ単独の処理時間ではない。

HTTP応答時間はcurlの `time_total` で、DNS・TCP・TLS・通信を含む。アプリ実行時間はWorkerログの最初の実行IDをDBの `wall_time_ms` と照合した。各試行のWorkerには最初の成功1件とウォーム5件の計6件が記録され、全18件が `succeeded` だった。

ウォーム15件は **85.9〜109.9ms、中央値94.2ms**。アプリ実行時間は3〜6msだった。3回のコールド試行と15件のウォーム試行から、p95・p99や可用性SLAは算出していない。

## 起動中の公開URLと待ち時間

準備中のリクエストは **HTTP 502** で失敗し、準備後のリクエストから成功した。監視プローブが最初に失敗した送信時点から、最初の成功応答を受け取るまでの観測時間は、順に約82.2秒・31.1秒・61.9秒。この値にはscale-downと、Worker数0を確認するための停止中の時間も含まれる。プローブ間隔があるため、正確な障害開始・終了時刻や一般的な再起動時の停止時間は表していない。

準備処理自体は約18.1秒で安定していた一方、WorkerのHTTPサーバー起動からコンパイル開始までは27.0秒・5.9秒・27.0秒だった。Workerの準備完了後にも、公開URLで成功するまで待ちが生じた。

実装ではControl Planeが新しいWorkerをDNSで検出し、公開リクエストの転送先にはReadyなWorkerを使う。実環境のCoreDNSは `ttl 30` / `cache 30`、準備処理の再確認間隔は5秒だった。これらの検出・readiness・DNSキャッシュによる待ちが、復帰時間のばらつきに影響したと考えられる。各要因の厳密な内訳は今回計測していない。

普段の速い応答は、常駐Workerでコンパイルと準備を先に済ませているため。現状の単一Workerを完全に入れ替えると、準備中に応答できる別Workerがいなくなる。この結果は、アクセスが途絶えたあとに毎回同じ待ちが発生することを意味しない。現構成にアイドル時の自動scale-to-zeroはない。

## 記録と制約

生のcurl計測・応答ヘッダー・Workerログ・Pod情報・DB照合結果は `.local/vps/cold-start/20260925T014903Z/`、実行スクリプトは `.local/vps/cold-start/measure.py` に保存した。起動処理は `finally` で元のレプリカ数へ復元する構成とした。

事前試行では、停止中の応答を503と想定していたスクリプトが502を受けて中断し、自動復旧を確認した。この試行は表の3回に含めていない。メトリクス取得用のPod proxyはタイムアウトしたため、キャッシュ消去の確認にはPod UID・emptyDir設定・キャッシュミスのログを使った。メトリクス取得は最初の成功応答・ウォーム測定が完了したあとに試しており、表の時間には含まれない。

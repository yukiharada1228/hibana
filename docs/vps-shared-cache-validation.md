# 共有コンパイルキャッシュの検証

検証日: 2026-09-25。数値とログは [vps-shared-cache-validation.json](vps-shared-cache-validation.json)。

既存のGarageへHibanaが生成したコンパイル結果を保存し、空のPodから再利用できることを確認した。連続3回のPod交換すべてで共有キャッシュにヒットし、再コンパイルは0回、HTTP 200だった。コードの準備は比較した1組で8.310秒から0.515秒へ短縮した。ただしPod交換全体の時間は短縮していない。準備開始前やReady反映までの待ち時間を含むためである。

## 環境と範囲

- [IaC検証](vps-iac-validation.md)の3台のARM64 VMを再利用。各2 vCPU・2GiB・swapなし、Ubuntu 24.04、kubeadm Kubernetes 1.36.5。
- Workerは1 Pod、CPU上限2、メモリ上限1,280MiB。実行ノードにはPostgreSQL・GarageとOSも同居する。
- 既存の`hello`を使用し、コンパイル済みファイルは54,466,512バイト（約51.94MiB）。アプリを追加・変更していない。
- 比較ごとにPod UIDが変わり、`emptyDir`は空。コンテナイメージはノード上に取得済みで、Control Plane、DB、Garage、OSのキャッシュは維持した。
- 新しいサービスやPVCは追加していない。公開VPS・DNS・npmは変更していない。

## コードの準備時間

同じイメージ・アプリについて、Worker側の共有キャッシュを無効／有効に切り替えた。`artifact prepared`ログの`elapsed_ms`を使用した。これは元Wasmの取得とコンパイル、または共有成果物の取得・認証・読込み・ローカル保存にかかった時間で、Pod起動やWorker発見の待ち時間は含まない。

| 条件 | 準備時間 | コンパイル回数 | 共有ヒット |
|---|---:|---:|---:|
| 共有キャッシュなし、ローカルも空 | 8,310ms | 1 | 0 |
| 共有キャッシュあり、ローカルは空 | 515ms | 0 | 1 |

各条件1回の比較であり、常に同じ倍率になることを保証しない。定期的な準備確認も同じログを出すため、初回の準備だけを集計した。最初の測定スクリプトでログが1件だけと仮定していた箇所を修正し、共有側を再測定した。

## Pod交換全体

初回だけ共有先にもデータがなく、その後は同じ保存済みコードを再利用した。時刻は交換操作の開始から、新しいPodがReadyとなり、そのアプリから最初のHTTP 200を受信するまで。

| 試行 | 操作開始→最初のHTTP 200 | 再コンパイル | 最初のHTTP要求自体 |
|---|---:|---:|---:|
| 初回、取得・コンパイル・共有保存 | 27.19秒 | 1 | 153.23ms |
| 交換1、共有から復元 | 30.71秒 | 0 | 76.86ms |
| 交換2、共有から復元 | 30.85秒 | 0 | 74.38ms |
| 交換3、共有から復元 | 32.01秒 | 0 | 63.40ms |

初回はDeployment更新、交換1〜3はPod削除による置換。操作方式も異なるため、全体時間をそのまま性能の倍率には使わない。追加の準備時間比較でも、共有ありではWorker起動から準備開始まで約19.4秒の待ちがあった。発見・名前解決・KubernetesのReady反映などを含む待ち時間は今回短縮しておらず、内訳の厳密な切り分けも未実施である。

各試行の後にHTTPSを10回呼び、本文も確認した。3回の交換後の中央値はそれぞれ24.07ms、14.81ms、13.95ms。Workerのコンテナ再起動・OOM Killは0だった。1秒間隔のcgroup観測では共有復元のメモリ使用量は最大約58〜59MiBだったが、短い割当てのピークを取り逃すため必要メモリ上限を示す値ではない。

## 認証・上限・互換性

- Wasmtimeの互換性ハッシュと元WasmのSHA-256をキーにする。同じCPU・エンジン設定に対応する成果物だけを選ぶ。
- HMAC-SHA-256を検証してからネイティブコードを読み込む。テナントがアップロードしたネイティブコードは受け付けない。
- 共有キャッシュは2GiB・256件を上限に、古い保存日時のものを回収する。元Wasmや別prefixは対象外。これは最新オブジェクトの論理サイズであり、Garageの物理的な回収待ちなどは含まない。
- 別プロセスのHTTP結合試験では、改ざんされた成果物を拒否して再コンパイル・修復すること、認証不備の書込み拒否、256件の上限、共有書込みが403でもローカルの準備と実行が成功することを確認した。
- Rust単体テスト321件とdoc test、DB/HTTP結合テスト、Clippy、RLS・構造チェック、CLIのPythonテスト245件、IaCテスト5件を実行した。鍵の追加では既存の資格情報を維持し、previewはファイルを書き換えない。

各Workerが全公開アプリを準備する方式と、Workerごとのローカルキャッシュ上限は変わらない。Workerを追加しても保持可能なアプリ総量が増える設計にはまだしていない。

## 復元

検証用クラスタのControl Plane・WorkerのDeployment設定と、追加した鍵の設定を元に戻し、既存`hello`のHTTP 200を確認した。試験で生成した約51.94MiBの共有キャッシュ1件はGarageに残る破棄可能な補助データで、元Wasmやアプリ設定は変更していない。一時停止した`hibana-dev`・`hibana-console`もデータを保持したまま復元し、API・Console・OIDCの疎通を確認した。ノードID・割当リソース・Deployment設定は試験前と一致し、最終結果をJSONに記録した。

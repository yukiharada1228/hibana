# 本番VPSでのコードキャッシュ実測

測定日: 2026-09-25。Hibana `0.2.0-rc.12`、commit `309b0671a2858b50a301302ac29ea9b50d6981e0`。ローカルVMの推定ではなく、公開中のKAGOYA環境で測定した。

[CI](https://github.com/yukiharada1228/hibana/actions/runs/36118660386)・依存監査・IaC検証に成功後、[リリース工程](https://github.com/yukiharada1228/hibana/actions/runs/36118819969)で全配布物とnpm公開後の取得を検証。Ansibleで本番へ適用した。測定後は3ノードReady、Control Plane/Worker/Consoleのrc.12稼働、HTTPSのConsole/API/OIDC discovery/hello、未完了実行0件を確認した。

## 条件

- KAGOYA 2 vCPU / 2GBプラン × 3台（各ノードの認識メモリは約1962 MiB）、kubeadm Kubernetes 1.36.5、Linux AMD64。実行Podは1個。CPU上限2、メモリrequest 768 MiB / limit 1280 MiB、同時実行8、ゲスト予約上限1024 MiB。
- `https://hello.demo.apps.hibana.cloud/` の同じバージョン・同じWasmを測定。元Wasm 12,393,107 bytes。既存アプリのコード・公開状態は変更しない。
- 操作Macから公開HTTPSへ毎回新しいcurl接続。計測値はDNS/TCP/TLS、API処理、必要なコード取得・検証・読込、アプリのHTTP応答を含む。実行履歴の保存は別途完了を確認し、応答計測に全保存処理が含まれるとは限らない。
- Workerのメモリ・emptyDirを空にするにはPodを交換。Readyを確認後、旧DNS応答のTTLを避けるため35秒待ってから最初のアプリ要求を測定。交換から復旧までの総時間と、このHTTP所要時間は別。OS・イメージレイヤー・CP/DB/Redis/Garageは稼働を継続。
- 比較の再コンパイル条件だけ、Workerプロセスから `COMPILED_CACHE_KEY` を外して共有コードを利用しない。Garageの元Wasm・共有オブジェクト・実際の鍵は削除しない。
- 容量超過の再現中はローカルディスクの論理キャッシュ上限を128 MiBへ一時縮小。通常の2 GiBへ最後に復帰。メモリLRUは実装既定の64件/256 MiB（コードサイズの重みでありRSS制限ではない）。

## キャッシュ経路の証拠

| 空キャッシュ試行 | HTTP | コード復元処理のログ | 共有hit | 再コンパイル | Pod交換→Ready |

| garage-1 | 481.568 ms | 377 ms | 1 | 0 | 6.764 s |
| garage-2 | 465.089 ms | 354 ms | 1 | 0 | 6.819 s |
| garage-3 | 483.127 ms | 384 ms | 1 | 0 | 8.297 s |

| source-2 | 18870.173 ms | 18765 ms | 0 | 1 | 6.816 s |
| source-3 | 18710.056 ms | 18556 ms | 0 | 1 | 8.382 s |

コード復元処理のログはWorker内の経過時間で、Garage転送だけでなく、認可付きURLの取得・HMAC検証・Wasmtime読込・ローカル保存・再認可などを含む。HTTP全体の時間と足し合わせない。

各試行で要求前の再コンパイル・共有hit・メモリhitが0、ローカル `.cwasm` が0件であることを確認。Garage条件は共有hitが1、再コンパイルが0。元Wasm条件は共有hitが0、再コンパイルが1。同時4要求も共有hitは1で、同じ復元結果を再利用した。

## 容量超過・復帰

- 8個の異なるHono Wasmを一時公開して3巡。24要求すべて共有キャッシュhit、再コンパイル増加0、Pod UID不変。アプリ切替えでPodは交換していない。
- 論理ディスク上限128 MiBに対して、計測中の保存量最大は110.80 MiB。常駐させず、使用に応じて退避・復元した。
- 実行Podのworking set最大は357.67 MiB（268サンプル）。各測定Podのコンテナ再起動0。これは実験全体のサンプル値で、瞬間最大や将来の上限を保証しない。
- 一時アプリ8件をAPIで削除し、試験用トークンも削除。公開helloのID・有効バージョン・削除状態が測定前と一致することを確認。
- Worker Deploymentをrc.12の通常設定へ完全に戻し、共有鍵利用・ディスク2 GiB・実行Pod1個、公開helloのHTTP 200と本文を再確認。

## 適用・制約

- 既存の秘密値とDBを暗号化して退避し、復号検証後にAnsibleで適用。VPSのCPU/メモリプラン、DBスキーマ、ユーザー・認証情報は維持。
- 更新前チェックでアプリ用・コンソール用Ingressの管理ラベル不足を検出。既存specとレンダリング結果の完全一致を確認して管理ラベルのみ補正し、再適用した。
- 適用中の監視は1秒間隔・応答待ち上限4秒。HTTP 502が2件、404が2件、4秒タイムアウトが9件あり、完了後は正常へ復帰した。この短い監視期限では初回コンパイルが完了せずキャンセルされるため、これを通常のコールド応答時間とはしない。本測定のcurl上限は120秒で、途中キャンセルしない。
- 最小VPS構成の更新方式は `Recreate`。本番更新と冷却試行で単一Podを交換しており、その間は短時間の利用不可がある。これを無停止更新の検証結果とはしない。
- 128 MiB制限は論理キャッシュ予算の実験。実ディスク全体のENOSPCは本番で発生させていない。一時ファイルや実行中のmmap参照は論理保存量と一致しない。
- 旧測定の26.6〜77.6秒はPod起動・事前コンパイル・到達確認を含む。今回のHTTP復元時間とは計測範囲が異なる。同条件で比較するには上表のrc.12内のGarage復元と再コンパイルを使う。
